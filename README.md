# 阳光食堂采购配送进销存一体化平台

## 1. 系统平台与总体目标

### 1.1 系统平台
- **PC 端**：功能最全面的管理后台，主要面向教体局管理员、乡镇中心校管理员、学校管理员、财务人员及供应商等需要进行复杂操作和数据分析的用户。
- **移动端 H5 版**：提供核心功能的移动网页版本，适配各类智能手机浏览器，方便用户随时随地进行订单查看、审批、签收等操作。
- **微信小程序**：深度集成于微信生态，提供便捷的访问入口和流畅的用户体验，尤其适合学校一线人员（如食堂管理员、验收员）进行快速操作。

### 1.2 总体目标
- **统一管理**：实现县级教体局对全县学校食堂业务的统一监管、乡镇中心校对其下属学校的集中管理。
- **流程电子化**：在符合现行财务与审计要求的前提下，最大限度推进业务流程线上化和单据电子化，显著减少纸质材料使用，确保数据可追溯。
- **管理智能化**：利用数据分析和预警机制，为采购计划、库存控制、成本核算和食品安全监管提供智能决策支持，保障师生饮食安全与质量。

## 2. 组织架构与权限

### 2.1 组织架构
- **监管层**：西畴县教育体育局 (教体局)，作为系统的最高管理和监管单位，负责系统的整体运行和顶层设计。
- **管理层**：
  - 县直属学校：直接隶属于教体局管理的学校，在系统中作为独立的管理单元。
  - 乡镇中心学校：负责管理其所在乡镇的多个下属学校（完小、教学点等），形成一个管理片区。
- **执行层**：各级学校（包括县直属学校和乡镇中心校的下属学校），作为食堂采购和管理的最终执行单位。
- **合作方**：配送公司（供应商），通过教体局审核入驻系统，为全县学校提供食材及物料。

### 2.2 用户角色与权限
| 角色名称 | 所属单位 | 核心职责与权限 |
|---------|---------|--------------|
| 系统管理员 | 教体局 | 最高权限。负责系统基础参数配置、组织架构维护、供应商入驻审核与协议签订、全县数据监控与分析、分配各级管理员账号与权限。 |
| 乡镇中心校管理员 | 乡镇中心学校 | 辖区管理权限。管理本乡镇所有下属学校的用户和基础信息；查看并分析辖区内所有学校的采购、库存、财务数据；可代下属学校进行部分操作（如订单管理）。 |
| 学校食堂管理员 | 各级学校 | 日常操作权限。负责本校的商品浏览、采购下单、订单修改、收货验收（拍照上传）、出入库登记、库存盘点、退换货申请等。 |
| 学校财务人员 | 各级学校 | 财务处理权限。负责核对月结单与学期结单、确认结算金额、管理发票信息、与供应商进行财务对账。 |
| 学校领导/监管人员 | 教体局、乡镇中心校、各级学校 | 数据查看权限。根据所在层级，查看对应范围内的各类统计报表（采购、库存、财务等），进行监督和决策，无操作权限。 |
| 供应商（配送公司） | 合作企业 | 商业运营权限。负责维护企业信息、管理商品目录（上/下架、定价、上传图片视频）、接收并确认订单、生成配送单、处理退换货、查看并确认结算单。 |

### 2.3 权限灵活性设置
- 为适应不同学校的管理能力和需求，系统需支持权限的灵活配置。
- 教体局或乡镇中心校可以根据实际情况，将部分管理权限下放或上收。例如：
  - 出入库管理权限：默认由各学校食堂管理员负责。但对于管理能力较弱的下属学校，其出入库管理可由其所属的乡镇中心校统一负责。此权限可在系统后台进行灵活设置。

## 3. 核心功能清单

### 3.1 供应商（配送公司）管理模块
- **入驻申请**：供应商通过系统公开入口在线提交入驻申请，填写公司基本信息，并上传营业执照、食品经营许可证等资质文件扫描件。
- **资质审核**：教体局管理员负责审核供应商提交的资料。审核状态分为"待审核"、"审核通过"、"审核驳回"。驳回时需注明原因，以便供应商修改后重新提交。
- **协议签订**：审核通过后，系统支持教体局与供应商在线签订电子合作协议，明确供货标准、配送要求、结算方式等条款。协议可在线预览和下载。电子协议与电子签字的使用，需符合国家相关法律法规要求，系统支持根据实际情况启用或关闭相关功能。
- **信息维护**：供应商可登录后台，维护其公司基本信息、联系方式、银行账户等。重要信息变更需经教体局审核。
- **商品管理**：供应商可管理自有商品库。支持单个或批量上架商品，商品信息包括名称、规格、产地、分类等。商品价格设定必须支持小数点后两位。
- **商品多媒体**：支持为每个商品上传高清图片和介绍短视频，以直观展示商品外观、品质和规格，提升采购透明度。
- **状态管理**：教体局可对供应商状态进行管理，如"合作中"、"暂停合作"、"已解约"。暂停合作的供应商将无法接收新订单。

### 3.2 订单与结算管理模块
- **商品浏览与下单**：学校食堂管理员可按分类或通过搜索浏览商品，将所需商品加入购物车，生成采购订单。
- **欠款下单**：系统支持学校在结算周期内进行欠款下单。订单生成时记录为应付款项，无需立即支付，计入月度或学期账单。欠款下单需在系统设定的结算周期、额度和审批规则内进行，相关参数由教体局统一配置，确保资金风险可控。
- **订单修改**：在每日订单截止时间之前，学校可自由修改订单中的商品种类和数量。超过截止时间后，订单将被锁定，不可修改。
- **订单确认与处理**：供应商接收订单后进行确认。若库存不足或信息有误，可驳回订单并注明原因。确认后，订单状态变为"待配送"。
- **退换货管理**：学校在验收时若发现商品问题，可发起退换货申请。支持对部分商品或部分斤两（如一箱苹果中退回2斤）进行退换。系统生成退换货单，经双方确认后，自动在结算单中抵扣相应金额。
- **单据生成与管理**：系统自动生成并管理以下关键单据：
  - 配送单：供应商确认订单后生成。
  - 验收单：学校确认收货后生成，可附带现场验收照片。
  - 月结单：每月自动生成，汇总当月所有订单金额。格式为三联单（会计联、制单联、送货方联），需多方签字确认。
  - 学期结单：每学期末自动生成，汇总本学期所有月结单。格式为三联单，需包含会计审核、制单人、送货方、校方负责人的电子或线下签字流程记录。

### 3.3 学校端管理模块
- **收货验收**：食堂管理员根据配送单，核对送达商品的品名、规格、数量、质量。支持通过移动端扫描配送单上的二维码快速调出订单信息。
- **拍照上传**：验收时，管理员必须对货品进行拍照并上传至系统，作为验收凭证，照片与验收单绑定，按国家及行业相关数据留存年限要求进行长期保存，便于追溯。
- **入库管理**：验收无误后，在系统中执行"一键入库"，商品数量自动增加到学校仓库库存中。系统自动生成入库记录，包含时间、商品、数量、验收人等信息。
- **出库管理**：食堂每日领用食材时，需在系统中进行出库登记，记录出库商品、数量及用途（如"午餐使用"）。系统自动扣减相应库存。
- **库存盘点**：支持定期（如每周/每月）或不定期的库存盘点。管理员录入实际库存后，系统自动生成盘点差异报告，支持盘盈盘亏调整。

### 3.4 财务与库存高级管理模块
- **月结库存处理**：系统需明确处理月结后剩余商品的归属问题。系统支持多种库存成本核算口径，具体采用方式应根据当地财务制度和主管部门要求进行配置。提供两种可配置的结算方式：
  1. 计为本月出库：月底盘点的所有剩余库存，其成本全部计入当月支出。
  2. 结转至下月：月底盘点的剩余库存，其成本不计入当月，库存数量和价值自动结转至下一月份的期初库存。
- **伙食费来源管理**：系统需支持两种伙食费来源的记录与核算：营养餐补助和自交伙食费。在进行财务核算和生成报表时，能够按资金来源对支出进行分类统计和展示，确保专款专用，账目清晰。
- **财务结算**：自动生成多维度财务报表，如月度/学期收支报表、成本构成分析报表、资金来源支出明细表等，支持导出为 Excel 或 PDF 格式。

### 3.5 数据分析与报表模块
- **采购分析**：按学校、乡镇、时间、商品类别等维度，统计分析采购量、采购金额、采购频率。生成采购排行、价格波动趋势图等。
- **库存分析**：生成库存周转率、库存预警、临期/过期商品报告等。帮助学校优化库存水平，减少资金占用和浪费。
- **数据驾驶舱**：为教体局、乡镇中心校和学校领导提供可视化数据驾驶舱，集中展示采购总额、食品安全预警、各校支出对比等核心指标，支持下钻分析。
- **报表导出与订阅**：所有报表均支持导出。关键报表（如全县采购汇总）可设置定时任务，自动生成并通过邮件或系统消息发送给指定负责人。

## 5. 非功能性需求

### 5.1 性能需求
- **响应时间**：核心操作页面（如登录、商品列表、订单提交页）在正常网络条件下加载时间应不多于 3 秒。
- **数据查询与报表生成**：对于常规的数据查询，响应时间应在 5 秒以内；对于跨度大、数据量大的复杂报表（如全县年度采购分析），系统应提供异步生成和下载功能，避免页面长时间等待。
- **并发处理能力**：系统必须能够稳定支持全县所有学校及供应商在高峰时段（如每日上午 8:00-10:00 的下单高峰）的并发访问。系统初期设计支持不少于 500 个用户同时在线，并具备平滑扩展能力。
- **数据处理效率**：批量操作（如批量导入商品、生成全县月结单）应在后台执行，并有明确的进度提示。每月/每学期结算单的批量生成任务应在 1 小时内完成。

### 5.2 安全性需求
- **数据传输安全**：全站必须启用 HTTPS 加密传输（TLS 1.2 及以上），防止数据在传输过程中被窃听或篡改。
- **数据存储安全**：用户密码、财务信息等敏感数据在数据库中必须经过加密（如哈希加盐）存储。数据库应有严格的访问控制。
- **权限控制**：严格遵循基于角色（RBAC）的权限模型，确保任何用户都只能访问和操作其权限范围内的信息和功能。禁止任何形式的越权访问。
- **安全审计**：系统必须记录所有用户的关键操作日志，包括登录、退出、数据增删改、权限变更、财务操作等，日志需包含操作人、时间、IP地址及操作内容，且日志不可被普通管理员删除或修改。
- **防范攻击**：系统需具备防范常见 Web 攻击的能力，如 SQL 注入、跨站脚本（XSS）、跨站请求伪造（CSRF）等。

### 5.3 可用性需求
- **界面设计**：界面应简洁、直观、友好，业务流程清晰，符合用户操作习惯。PC 端、H5 和微信小程序应保持统一的视觉风格和核心交互体验。
- **易操作性**：日常高频操作（如下单、验收）应尽可能简化步骤。对于不熟悉系统的用户，应能通过直观的界面引导完成主要任务，降低学习成本。
- **帮助与引导**：在复杂功能页面提供必要的帮助文档、操作提示（Tooltip）或视频教程入口。
- **错误处理**：提供友好、明确的错误提示信息。当用户操作错误时，应能清晰地告知错误原因及修正方法，而不是显示模糊的系统代码。

### 5.4 可靠性与稳定性需求
- **系统可用性**：系统需保证 7x24 小时运行，年可用性不低于 99.5%（即全年累计故障时间不超过 43.8 小时）。
- **数据备份与恢复**：系统需建立自动化的数据备份机制，每日对数据库进行完整备份。需制定详细的灾难恢复预案，确保在发生服务器故障、数据损坏等极端情况下，能在规定时间内（如 4 小时内）恢复系统服务，并将数据丢失控制在最小范围（如最多丢失 24 小时内的数据）。
- **容错能力**：系统应具备一定的容错能力，单个模块的临时故障不应导致整个系统崩溃。

### 5.5 兼容性需求
- **浏览器兼容性**：PC 端应兼容主流浏览器的最新版本，包括 Google Chrome、Microsoft Edge、Firefox 等。
- **移动端兼容性**：移动端 H5 及微信小程序应良好适配近三年主流的 iOS 和 Android 操作系统及设备。

### 5.6 可扩展性与可维护性需求
- **模块化设计**：系统应采用模块化、低耦合的架构设计，便于未来新增功能模块（如食品安全溯源模块、学生营养分析模块）或对现有模块进行升级改造。
- **代码规范**：后端和前端代码需遵循统一的编码规范，并附有必要的注释，便于团队协作和后期维护。
- **部署与扩展**：系统架构应支持水平扩展，当用户量和数据量增长时，可通过增加服务器节点来提升系统处理能力。
